# GHL API v3 Phase 2c: AI/Communication Resource Coverage — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add ~39 new tools covering GHL API v3's AI/Communication resources
(`conversation-ai`, `voice-ai`, `chat-widget`, `agent-studio`).

**Architecture:** Four new tool modules, each following the exact pattern established
in Phase 1/1.5/2a/2b (`ghl_<verb>_<noun>` naming, Zod `inputSchema`,
`handler(args, config)` → `ghlRequest(...)` → `JSON.stringify` or `formatError`). Every
call uses `version: GHL_VERSION_V3`. Read the real request/response schema from the v3
spec file before writing each tool.

**Tech Stack:** TypeScript, Zod, Vitest, Node.js (existing stack — no new dependencies).

## Global Constraints

- Spec: `docs/superpowers/specs/2026-08-04-v3-phase2c-ai-design.md` — read it before
  starting. `agent-studio`'s 3 `public-api/*` operations are explicitly deprecated in
  the spec — do not build tools for them.
- v3 OpenAPI specs: `/Users/nerdsnipe/WebstormProjects/highlevel-api-docs/apps/v3/<resource>-v3.json`.
- Tool naming: `ghl_` prefix, snake_case.
- Every `ghlRequest` call: `version: GHL_VERSION_V3` (imported from `../client.js`).
- **Disclose malformed/ambiguous upstream spec fields with a one-line code comment**
  as you write each tool, not as an afterthought — this has been an inconsistently
  applied habit across prior sub-phases; apply it every time this phase.
- **Verify `locationId` presence/absence per endpoint — don't assume.**
  `POST /conversation-ai/agents` has no `locationId` parameter anywhere in its real
  schema (confirmed during design research); don't force-inject one. Other endpoints in
  this phase may differ. Check each one.
- **Do not trim "large" required-field lists** — this codebase has a documented history
  (Phase 1's `custom_fields.ts`, Phase 2b's near-misses) of getting this wrong; always
  implement the full `required` array from the real schema.
- TDD throughout: write the test first against the real schema, confirm RED, implement,
  confirm GREEN.
- Each task registers its new tool array into `ALL_TOOLS` in `src/index.ts` and adds a
  `toHaveLength()` assertion plus `expectedTools` manifest entries (with correct running
  total) in `tests/server.test.ts`. Keep `expectedTools` accurate every task.
- README/CHANGELOG updates are consolidated into the final task.
- Do not bump `package.json`'s version, tag, or publish.

**Do NOT build tools for** `GET /agent-studio/public-api/agents`,
`GET /agent-studio/public-api/agents/{agentId}`,
`POST /agent-studio/public-api/agents/{agentId}/execute` — all three are marked
`"Deprecated"` in the spec's operation summaries.

**Two distinct "update" operations — don't conflate them.** Design research already
confirmed:
- `ghl_update_agent_studio_agent_metadata` (`PATCH /agent-studio/agent/{agentId}`):
  required `locationId`; optional `name`, `description`, `status` — updates the agent's
  top-level metadata/status, not its workflow definition.
- `ghl_update_agent_studio_agent_version` (`PATCH /agent-studio/agent/versions/{versionId}`):
  required `locationId`; optional `versionName`, `description`, `nodes`, `edges`,
  `globalVariables`, `inputVariables`, `runtimeVariables`, `globalConfig`, `userId`,
  `userName` — updates the versioned workflow definition itself. `nodes`/`edges` are
  almost certainly complex nested workflow-graph structures; model them permissively
  (`z.array(z.record(z.unknown()))`) rather than fully typing them out, matching the
  established Phase 2a/2b precedent for deeply nested bodies. Make the distinction
  between these two tools explicit and clear in both tools' `description` fields so an
  LLM caller picks the right one.
